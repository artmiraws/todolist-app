# AWS access (dev)

How the application is reached in the AWS `dev` environment, and why it is built this way.

## Hostname and TLS

- Hostname: `dev.todolist.<base_domain>` (published as the SSM parameter `/todolist/dev/app_hostname`).
- TLS: an ACM certificate, DNS-validated through the existing Route53 zone. The Ingress sets
  `alb.ingress.kubernetes.io/certificate-arn` and redirects HTTP to HTTPS.
- DNS: ExternalDNS creates the Route53 record from the Ingress host.

## Traffic flow

```text
Browser -> Route53 (dev.todolist.<base_domain>) -> ALB -> Ingress -> Service -> app pods
```

## Ingress with ALB vs Service type LoadBalancer

- This project uses an **Ingress** with `ingressClassName: alb`. The AWS Load Balancer Controller
  creates an Application Load Balancer (L7) and routes by host/path. This is the intended pattern and
  what integrates with ACM and ExternalDNS.
- A literal **`Service type: LoadBalancer`** would normally be handled by the cloud controller and
  create a Network Load Balancer (L4), without host/path routing or ACM integration. It is not used
  here; the Service is a plain ClusterIP behind the Ingress.

## Values needed for access

The cloud values file (generated by CI, not committed) provides:

- `ingress.host` - the documented hostname.
- `ingress.annotations` - `scheme`, `target-type: ip`, `listen-ports` (HTTPS 443), `ssl-redirect`,
  and `certificate-arn` (from the SSM parameter `/todolist/dev/ingress_certificate_arn`).

## Dev limitations

- Dev uses disposable synthetic data and non-reused credentials.
- TLS is in place, but the environment is still a proof of concept: single NAT, single Aurora writer,
  small node. It is not production.
- End-to-end browser checks against the documented hostname are part of DEV-VERIFY (EPIC-9).
